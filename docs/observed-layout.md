- Debian kernel 6.12.113+deb13-amd64, package 6.12.113-1.
- Guest cryptsetup/libcryptsetup 2:2.7.5-2; host cryptsetup 2.8.4.
- Userspace codec: Python cryptography 46.0.5, AESGCM implementation.
- Raw image: 134,217,728 bytes; primary data: 115,687,424 bytes in 28,244 sectors.
- Primary SHA-256 independently agrees between the guest's stock mapper and
  userspace: b54b4937b0a9539574c7525d1634b3052cbb3836ca8d46211bb1cf03e4aaf1c4.
- Ten automated tests passed with this fixture, including all-sector verification,
  unchanged raw-image digest, incorrect key, ciphertext/tag/IV corruption at four
  boundaries, truncated images, and nonempty/torn journal rejection.

Subsequent output-image checks passed in artifacts/verify-001 for four random-IV
replacements and artifacts/verify-packed-001 for a full hidden-payload pack.
Stock Linux authenticated all primary bytes and raw-image hashes before/after
read-only activation matched. The packed carrier changed all 28,244 IVs with no

observer with snapshots and the primary key can detect this reencrypt activity.

This is evidence for the tested profile and compatible modifications. It does
not establish hidden payload security, arbitrary configurations, hardware crash

## LUKS and integrity parameters

LUKS2 has one dynamic crypt segment with offset 16,777,216 bytes, zero iv_tweak,
aes-gcm-random encryption, 4096-byte encryption sectors, and aead integrity.
Journal encryption and integrity algorithms are both none. The primary key is
32 bytes. The observed 28-byte tuple is 16 bytes of GCM tag followed by 12 IV bytes.

The integrity superblock begins at the segment offset and has magic integrt
followed by NUL, version 4, log2 interleave sectors 15, tag/tuple size 28,
journal_sections 7, provided_data_sectors 225952, flags 8 (fixed padding), and
log2 sectors per block 3. All superblock fields discussed here are little-endian;
addressing sectors are 512 bytes unless stated otherwise.

Journal entry size is round_up(8 + 8*8 + 28, 8) = 104 bytes. There are floor(504/104)
= 4 entries per metadata sector, eight metadata sectors per section, and eight
data sectors per entry. A journal section is therefore 264 sectors. Superblock
plus journal occupy 8 + 7*264 = 1856 sectors.

Each metadata run has round_up(28*(32768/8), 4096)/512 = 224 sectors, followed by
32768 primary data sectors. For primary encryption-sector index i, let:

    logical512 = 8*i
    area, within = divmod(logical512, 32768)
    base = segment_offset + (1856 + area*(32768 + 224))*512
    ciphertext_offset = base + (224 + within)*512
    tuple_offset = base + (within/8)*28

AAD is LE64(logical512) followed by the 12 stored IV bytes. In particular, the
address in AAD is measured in 512-byte units even though encryption sectors are
4096 bytes; using i directly would fail authentication for nonzero i.

## Conservative journal handling

There is no generic clean-journal flag to trust in this profile. The parser checks
every journal sector's trailing commit ID, normalized by section and sector
indices, against the four no-crypto upstream commit constants. IDs must agree
within each section. Every journal entry's sector_hi field must be 0xffffffff,
the unused marker. It rejects populated, malformed, encrypted, MACed, bitmap,
recalculating, inline, alternative-version, or unknown-flag profiles.

This deliberately rejects recoverable journals rather than replaying them. It
does not implement full journal ordering or recovery semantics. The kernel's
postsuspend path drains writes and initializes unused journal entries after
journal writes; the independently produced closed fixture satisfies these
checks. A future writer needs its own compatibility/crash evidence and must not
infer that dm-integrity protects raw userspace edits.

Relevant upstream functions in the source subset pinned by environment/sources.json:
crypt_convert_block_aead, iv_tag_from_dmreq, calculate_journal_section_size,
calculate_device_limits, get_data_sector, get_metadata_sector_and_offset,
init_journal, replay_journal, and dm_integrity_postsuspend. Debian patch
equivalence has not been established by full source comparison; independent
kernel readback provides the current behavioral check.

## Stock 512-byte profile

artifacts/control-512-001 uses the same pinned kernel and cryptsetup, with
--sector-size 512 and otherwise the same formatting options. Its stock full
primary readback agrees with the independent codec:
b49cb8f2559a3acf6d265ded9aab425f28e3488dcf68885f25fd5942c5eee5b2.
The 128 MiB raw image contains 214,800 primary sectors (109,977,600 bytes),
providing 4,475 complete hidden records (2,291,200 logical hidden bytes).

The superblock differs in log2_sectors_per_block=0, journal_sections=23 and
provided_data_sectors=214800. Journal entries are 48 bytes, ten per header
sector; each section occupies 88 addressing sectors. Initial space is
8 + 23*88 = 2032 sectors. A metadata run occupies 1792 sectors. The stock
integrity table omits block_size:512 (the default), reports journal_sectors:2024
and buffer_sectors:128. For 4096-byte sectors those values are block_size:4096,
journal_sectors:1848 and buffer_sectors:32. The smaller buffer in the latter
profile results from alignment to its metadata run, not a custom test option.

For either profile let f=primary_sector_size/512. Journal entry size is
round_up(8 + 8*f + 28, 8), section size is 8 + 8*f*floor(504/entry_size), and
metadata-run size is round_up(28*(32768/f), 4096)/512. Use the actual superblock
journal-section count to compute initial space. Replace 8 by f, 1856 by the
computed initial space and 224 by the metadata-run size in the offset formula
above. AAD remains LE64(i*f) || IV12. The parser checks LUKS/superblock sector-size
agreement before accepting an image.

These formulas were checked against the pinned v6.12.113 dm-integrity source
(calculate_journal_section_size/calculate_device_limits) and the independently
generated stock fixtures. Format defaults depend on geometry and versions;
the two fixtures do not establish arbitrary-profile support.

## Stock ChaCha20-Poly1305 profiles

artifacts/chacha-control-4096-001 and chacha-control-512-001 use the same pinned
kernel/cryptsetup and shared generator, with --cipher chacha20-random,
--integrity poly1305 and --key-size 256. Both passed stock full-primary readback
and independent cryptography ChaCha20Poly1305 authentication of every sector.
Their deterministic primary hashes match the same-sector-size AES fixtures
above by construction; their keys, UUIDs and encrypted raw images are different.

LUKS records encryption=chacha20-random, integrity.type=poly1305, with no journal
crypto. Cryptsetup maps this to capi:rfc7539(chacha20,poly1305)-random with
external AEAD integrity. Stored metadata remain tag16 || IV12; AAD remains
LE64(primary_sector_index * primary_sector_size/512) || IV12. Capacities,
superblock fields, journal strides, interleave offsets and lower integrity-table
options exactly match the AES fixture of each sector size. No carrier geometry
or hidden-record encoding change is needed.

The mappings and tuple sizing were checked against the pinned cryptsetup
cipher_dm2c and INTEGRITY_tag_size implementations. Linux's rfc7539 template
uses a 12-byte IV and a 16-byte authentication tag; it is distinct from the
8-byte-IV rfc7539esp template, which this prototype does not accept. The native
primary crypto path (dm-piv.c piv_aead) reproduces pinned dm-crypt's layout; userspace verification selects the
maintained AESGCM or ChaCha20Poly1305 primitive only after validating the exact
LUKS cipher/integrity combination. Active owner tables are checked against that
selection on setup and reuse. Neither profile changes the hidden nonce policy
or its documented limits.

## Stock original AEGIS-128 profiles

artifacts/aegis-control-4096-001 and aegis-control-512-001 use the same pinned
Linux/cryptsetup and shared stock generator, with --cipher aegis128-random,
--integrity aead and --key-size 128. Stock full-primary readback agrees with the
independent pinned SUPERCOP AEGIS-128 AES-NI reference. This original five-state
algorithm is distinct from AEGIS-128L in current libaegis/libsodium.

LUKS encryption is aegis128-random; the active transform is capi:aegis128-random.
Its ordinary metadata tuple is tag16 || IV16 (32 bytes). Linux's primary AAD is
LE64(primary_sector_index * primary_sector_size/512) || IV16. The pinned
crypto/aegis128-core.c declares a 16-byte key/nonce and accepts 16-byte tags;
cryptsetup's existing random-IV sizing supplies the matching ordinary tuple.
No custom IV length or clear hidden metadata is used.

| Primary sector bytes | Primary sectors | Decoy bytes | Hidden bytes | Metadata-run sectors |
| --- | ---: | ---: | ---: | ---: |
| 4096 | 28,216 | 115,572,736 | 400,896 | 256 |
| 512 | 213,008 | 109,060,096 | 3,028,992 | 2048 |

The two superblocks retain version4, interleave15 and flags8, with block3/0,
provided_data_sectors225728/213008 and journal_sections7/23. Journal strides
remain 104/48 bytes and section sizes264/88 addressing sectors: rounding absorbs
the extra four tuple bytes. Substitute tuple_size32 for28 in the geometry
formulas above. The ordinary lower table uses buffer_sectors:128 at BOTH primary
sector sizes; block_size:4096 is explicit only for the 4096 profile. Journal
sectors remain1848/2024. These are observed defaults, not prototype overrides.

Every 576-byte hidden record consumes exactly36 full 16-byte IVs. Complete groups
and incomplete tails are derived from the actual primary count; all IV bytes are
used. The hidden encoding and public context remain v3. The widened RAM control
ABI is version2; no disk padding or legacy control decoder was added.
